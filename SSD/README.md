## 冲突处理顺序

发生冲突时，按以下顺序执行：

1. 经人工审阅后的 [`requirements.md`](./requirements.md)。
2. 最新修改意见 [`../Yining/spec/需求.md`](../Yining/spec/需求.md) 及其截图。
3. 原始业务要求 [`../Yining/需求.md`](../Yining/需求.md)。
4. 当前代码行为和 [`../app/docs/digital-pioneer-2026.md`](../app/docs/digital-pioneer-2026.md)。
5. 其他旧文档、测试名称或历史实现。

当前代码与需求不一致时，不得悄悄把现状写成需求；应在 `tasks.md` 标记为“待实现”或“待验证”。

## AI 开发协议

开始任务前：

1. 读取本目录全部四个文件。
2. 执行 `git -C ../app status --short`，保护人工和其他代理的未提交修改。
3. 在 `tasks.md` 选择一个状态为“待实现”或“待验证”的最小任务。
4. 先补失败测试，再改最少代码；复用现有 React、Mantine、Spring Boot 和测试设施，不新增依赖。
5. 不改写带反引号的英文文案，不复制 `Yining/spec/image/` 中的图片。
6. 完成后记录实际命令和结果；没有新鲜测试输出时不得标记“已验证”。
7. 若需求仍有歧义，停止编码并请求人工决定，不根据截图猜测业务规则。

## 需求 ID

需求使用稳定前缀，便于代码、测试和任务互相引用：

- `DP-GEN-*`：全局质量和文案
- `DP-HOME-*`：首页首屏
- `DP-OVR-*`：奖项概览
- `DP-TRACK-*`：奖项赛道
- `DP-TIME-*`：时间线
- `DP-NOM-*`：提名
- `DP-BROWSE-*`：候选人浏览
- `DP-VOTE-*`：员工投票
- `DP-JUDGE-*`：组委会评分和排名
- `DP-ERR-*`：错误与空状态

现有 ID 不得重新编号。删除需求时保留 ID，并标记为废弃及原因。

## 维护流程

需求变化时只做四步：

1. 人工确认变化。
2. 更新 `requirements.md` 中对应 ID。
3. 同步 `design.md` 的文件/数据影响。
4. 在 `tasks.md` 新增或重开任务，并附验证证据。

不要让 AI 仅根据代码反向覆盖需求，也不要在多个文件重复维护同一段精确文案。
