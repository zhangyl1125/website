# /awards 性能诊断记录

检查日期：2026-10-10。用户已确认实际端口为 80，目标为 http://localhost/awards。

结论：发现已损坏的字体和视频、可复现的前端请求等待链，以及实际发生的代理 API 间歇超时。当前证据不足以给出稳定在线人数上限。本次诊断未修改业务代码、数据库内容和部署配置；仅新增本报告及脱敏测量结果。结束时工作区出现 AwardManagement.tsx、DigitalPioneer.css 的其他改动，本次未修改或覆盖它们；结论针对本轮检查的已部署版本，后续源码变化需要另行验证。

**范围与可比性**

- 实际部署为 Nginx → 单实例 Spring Boot → PostgreSQL，另有 MinIO。已校验已部署首页、主 JS、奖项页 JS 与本地 dist 相同；两份字体和视频与本地 public 文件逐字节哈希一致。
- 当前真实规模：11 个用户资料、1 个活动、10 条提名、3 条评委分配、14 条评分记录。容量测试只覆盖这个小数据集。
- 主机内存约 125.6 GiB，nproc 可用 CPU 为 30；同时运行多个其他项目。网站 API、前端容器均没有显式 CPU/内存硬限制。当前主机实测不适用于任意目标服务器，也不代表仅给网站独占这些资源。
- 已部署 application.yml 的 Hikari maximum-pool-size=10、minimum-idle=2、connection-timeout=20000；未发现对应的环境变量覆盖。PostgreSQL max_connections=100。10 条数据库连接不是 10 个在线用户。
- 未获取真实登录凭据或复用用户浏览器会话。真实读取测试仅访问公开活动和公开提名 API；登录后的奖项管理 UI 使用浏览器请求拦截与虚构管理员数据检查等待链。模拟 UI 测试没有通过服务器认证，不能作为真实管理接口吞吐量。
- 没有进行投票、评分、报名、上传或账户写入压测。没有进行长期 WebSocket 承载测试或真实用户网络测试。

**1. 静态资源损坏，已经验证，优先修复**

| 文件 | 实际字节 | WOFF2 头声明字节 | 结果 |
|---|---:|---:|---|
| public/fonts/award-sans-regular.woff2 | 2,359,296 | 2,477,912 | 浏览器解码失败 |
| public/fonts/award-sans-bold.woff2 | 2,359,296 | 2,585,300 | 浏览器解码失败 |

Chromium 报告 `Failed to decode downloaded font`、`Failed to convert WOFF 2.0 font to SFNT`；两份 FontFace 的状态均为 error。说明下载了约 4.72 MB 字体，最终却回退到系统字体。index.css 已有 font-display: swap，不能把所有等待时间都归于字体阻塞。

public/media/tech-blue-loop.mp4 为 2,359,296 字节、1920×1080、30fps，容器声明 16 秒；完整解码时出现 `Invalid NAL unit size`、`partial file` 和 `Invalid data found when processing input`。可以开始播放不等于文件完整。这个缺陷能解释背景播放异常，但尚未证明它独立导致整个页面卡住。

三份文件恰好都是 2,359,296 字节，结合格式声明和解码失败，强烈提示某个文件传输或打包环节截断；尚未定位具体环节。

隔离浏览器的一次冷缓存、模拟管理员单活动访问，36 条静态资源记录总 transferSize 约 7,697,938 字节（7.70 MB，包含响应头），其中两份字体和视频约 7.08 MB。这个数字随视频 Range 请求、缓存和浏览器有所变化。仅作量级示例：10 Mbps 链路顺序传输 7.70 MB 的带宽时间约 6.2 秒，不等同于首屏必然要等待这么久。

优化：从可信原始素材恢复同一字体和同一视频的完整文件，校验长度与哈希并实际解码；发布时使用新版本 URL，避免浏览器继续使用一年 immutable 缓存中的坏字体。随后对字体按字符覆盖范围做子集拆分、对视频重编码压缩，保留需要的中英文字符、字重、背景内容及循环行为。不能只把损坏文件改名或直接转码后认为恢复了丢失内容。

定位：app/hackhub-app/src/index.css:2、:9；src/pages/LandingPage.tsx:16、:66；public/fonts/；public/media/。

**2. 真实的间歇性代理超时，已捕获；根因仍需确认**

低频探针每轮并行发出 3 个 GET，约每秒一轮，共 20 轮：

| 路径 | 样本数 | 最大耗时 | 超时 |
|---|---:|---:|---:|
| 80 /health | 20 | 1.98 ms | 0 |
| 80 /api/v1/public/awards | 20 | 2,001.16 ms | 1 |
| 8080 /api/v1/public/awards | 20 | 3.50 ms | 0 |

异常轮时间为 2026-10-10 07:42:57 UTC（北京时间 15:42:57）：Nginx 健康页 0.82 ms，代理 API 在客户端 2 秒上限超时，直连 API 2.62 ms。请求几乎同时发出，支持“代理转发路径存在偶发停顿”的判断，但不能仅凭一次对照断言 Nginx 本身的具体缺陷。

同时段主机检查发现 I/O 等待：vmstat 独立短时样本 wa=56%、64%；另一组样本从 5% 上升至 54%，阻塞进程数最高 29。/proc/pressure/io 的 some avg10 约 78%、full avg10 约 77%，而 CPU 压力很低。异常探针同轮 some avg10=78.27%。这是主机存储压力的直接证据，但尚未建立磁盘压力与代理超时的因果关系。

API 和前端容器没有重启；探针后独立访问又恢复到毫秒级。Docker DNS 将 api 解析到当前 API 容器，未发现重复地址。日志汇总存在客户端放弃请求的 499；截取范围内未发现 API WARN/ERROR，也未发现 `upstream timed out`、`connect() failed`。测试客户端的 2～3 秒截止早于代理默认截止，不能用无代理超时日志来排除停顿。

优化/排查：

- 先添加仅含方法、$uri、状态、request_time、upstream_connect_time、upstream_header_time、upstream_response_time 的时序日志；不要记录 Authorization、Cookie、请求正文或带敏感参数的完整 URL。
- 同时采集代理 TCP 连接耗时、宿主机/容器网络、磁盘 await/队列、数据库等待、JVM GC、连接池 active/pending，将同一时间点串起来；目前管理 metrics 端点未授权访问，不能宣称已测到连接池耗尽。
- 检查共享服务器的大规模文件写入、构建、备份、日志写入与数据库磁盘竞争，按证据错峰或隔离存储。不要依据当前结果直接停掉其他项目或认定磁盘硬件损坏。
- 当前 Nginx 1.27.5 配置未定义 API upstream keepalive 连接池，可评估复用上游连接、减少反复建连；这属于可测量的优化候选，尚未验证能修复本次停顿。配置依据见 [Nginx 官方 keepalive 文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)。

**3. 奖项列表的多余等待，代码与隔离浏览器都已验证**

AwardManagement.tsx:82～93 先加载全部活动，再 Promise.all 查询每个活动的评委，等所有查询完成才关闭列表 loading。管理员也走相同路径，尽管列表显示不需要评委资料。进入单活动详情又会重新扫描活动列表与所有评委。

- 虚构 1 个活动、评委 API 即刻响应：约 502 ms 出现列表；这是一次本地冷上下文采样，不是统计分位数。
- 相同类型样本、人为让评委 API 延迟 1.5 秒：约 2,361 ms 出现列表。证明无关评委查询能阻塞整个列表；时间差不是严格 A/B 基准。
- 虚构 100 个活动：实际发出 100 个评委请求；与真实数据只有 1 个活动的现状不同，不能拿它解释所有当前慢请求。

保持功能的优化：管理员/管理者列表只获取展示所需的活动；只有详情需要读取当前活动的评委。普通评委利用已有 judge-assignments 接口过滤分配范围，同时保留后端权限校验和现有活动可见范围。列表与详情数据按用户和活动缓存并去重，在新增/删除活动、评委分配和状态变化后明确失效。不要把管理员查询结果共享给普通用户。

App.tsx 和 LandingPage.tsx 都调用 useAwardAccess，非管理者会各自请求分配；可合并缓存。apiClient.ts:54、:88 的并发 401 请求会各自刷新令牌，没有共享进行中的刷新任务；可做单次刷新合并，保留失败时的退出和重试语义。这两项是代码层面风险，未用真实过期会话复现。

**4. 后端查询随人数/提名数增长**

- GetHackathonJudgesUseCase.java:26～27：获取评委后循环 findById 读取个人资料。评委 J 人时，存在 1+J 类查询模式。可以 findAllById 批量加载，再保持原顺序组装响应。
- GetJudgeScoresUseCase.java:77～78：每个提名单独计算投票人数及加权分；有团队时还查询团队名。N 条提名至少存在 2N 次附加聚合调用。可按活动分组批量汇总，保持计分公式、精度、缺分处理和排名一致；需要使用既有评分测试及等价数据回归验证。
- 详情页一次加载全部用户供评委选择，未来用户增多时可改成服务端搜索分页，保留“所有可选用户都能搜索到”和已分配用户过滤规则。
- 已有一批外键/过滤索引，不宜直接重复添加。先以实际 SQL 的执行计划确认扫描量。
- 不建议先把数据库池从 10 改为很大的数字；先缩短单请求查询时间，再结合连接等待与数据库负载调整。[HikariCP 官方池大小说明](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)也强调更大的连接池并不必然更快。

**5. 并发测试结果与人数结论**

瞬时闭环读取测试，每个接口在并发 1/10/25/50 下分别执行 20/200/250/500 次请求，校验 HTTP 200 与 JSON content 列表。最高并发阶段非常短：

| 接口 | 并发连接 | 请求数 | 阶段时间 | P95 | 错误 |
|---|---:|---:|---:|---:|---:|
| 公开活动 | 50 | 500 | 0.120 s | 26.75 ms | 0 |
| 公开提名 | 50 | 500 | 0.239 s | 28.59 ms | 0 |

这些突发测试只能表明低延迟窗口中的短时读取能力；其计算出的高 RPS 不作为持续吞吐量，更不能折算为数千人在线。

随后进行限速测试：每客户端每 200 ms 最多发一个请求，两个公开接口交替，每档计划 50 次/客户端（约 10 秒）。单请求最多等待 3 秒；任何错误或耗时超过 1 秒即停止后续请求和升压，已在途请求可能继续到自身截止。

| 轮次 | 读取客户端 | 实际请求数 | 阶段时间 | 错误 | 说明 |
|---|---:|---:|---:|---:|---|
| 首次 | 10 | 282 | 8.61 s | 10 | 约 3 秒超时，停测 |
| 复测 | 10 | 500 | 9.81 s | 0 | 活动/提名 P95 分别 3.44/5.76 ms |
| 复测 | 25 | 883 | 10.01 s | 25 | 约 3 秒超时，停测，未执行 50 档 |

复测 25 客户端的 P95 仍仅约 5～9 ms，但已经有 2.83% 请求超时，说明只看平均值或 P95 会漏掉严重尾延迟。首轮失败率为 3.55%。首次测试汇总来自当次终端结果，复测原始汇总保存在 paced-results.json。

**不能把上述结论写成“最多 25 人”或“保证 50 人”。** 客户端是限速发请求的测试线程，没有真实登录、浏览器多资源下载、评分/投票行为或长连接。闲置在线人数、活跃操作人数、同时请求数是不同指标；本次未寻找饱和极限。当前共享环境连低负载代理读取都存在波动，无法负责任地承诺 100/500/1000 人稳定使用。

在资源完整性与代理波动解决后，需要在隔离测试数据和可用测试账号条件下，按目标业务规模分别测登录、浏览、投票、评分、排行榜和 WebSocket，采用多个不同账号而非共用一个投票账号；从 10/25/50/100 活跃用户逐档验证，至少覆盖 10～30 分钟、令牌刷新以及集中提交。写入测试应在隔离数据集进行。

建议验收目标（待结合业务确认）：业务 API P95 <500 ms、P99 <1 s、错误率 <0.1%，无持续数据库连接等待，后台任务期间也满足指标。再根据“每人每分钟实际操作次数 × 每次操作请求数”把可持续业务 RPS 换算为活跃用户预算，并给资源留余量；不要使用本次公开列表的瞬时 RPS 做换算。

**已经排除/已有的优化**

- 已开启 JS/CSS gzip、哈希静态文件缓存和页面路由懒加载，不把“启用 gzip/路由拆包”列为尚未实施的首要方案。
- Canvas 最终 CSS 为 position: fixed。100 条虚构活动的页面高度达到 22,687px，但 Canvas 始终为视口大小，窗口 resize 后也没有变成整页大画布。先前源码检查产生的“大列表扩大画布”怀疑已被运行验证排除。
- 动画已有后台隐藏、减少动态效果偏好处理和闲时停止 Canvas 机制。背景视频的完整性与资源大小优先于删除现有动效。
- 没有足够证据证明当前机器缺内存或 API 持续 CPU 饱和；短时负载快照不能代替长期监控。

建议实施顺序：恢复完整资源与缓存版本 → 定位代理超时/共享 I/O → 去掉管理员列表无关评委请求 → 批量数据库查询与请求去重 → 在目标配置和真实业务规模下重新定容。所有改动需保留权限、投票额度、计分规则、活动可见性、实时通知和展示内容。
